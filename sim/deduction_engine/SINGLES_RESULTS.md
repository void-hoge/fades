# Singles-only: サイクル測定と多コア・供給系の検討

追跡issue: [#13](https://github.com/void-hoge/fades/issues/13)。

測定日: 2026-11-05。Verilator 5.006、基準revision
`c46d7ae7cd1c004f508043dd2ffafaa2293a3c9f` に本実験の変更を加えたもの。

## 結論

- **Kaggle 100万問は全問がSinglesだけで解け、平均4.899026 cycle/問。**
  Locked Candidates併用は4.298587 cycle/問。同クロック・同コア数では併用が有利だが、
  Singles化によってコア数×クロックを **1.139683倍超**にできれば演算能力は逆転する。
- 演算のみなら6コア100 MHzで **122.47 M問/秒**。ただし現行の転送形式では
  128-bit × DMA実187.5 MHz ÷ 64 byte = **46.875 M問/秒/方向**が上限。
  現行転送系のままコアを増やしても、このKaggle集合では効果が小さいと予想される。
- **BRAMも制約になる。** 既存6コア実装は128/144 BRAMタイル使用。
  推論規則を減らしても各コアの729 bit × 1024段のRAMは減らない。
  多数のSingles専用エンジンを置くには、探索RAMと問題待ちキューの構成変更が必要。
- 17ヒント集合はSinglesだけだと55.44%が停滞し、難問集合は全問停滞する。
  これらを解き切る場合は探索コストを含める必要がある。

## 1. 測定対象・数え方

両構成とも `SEGMENT_RULES=0`。比較するのは以下の2つ。

|名前|Naked Single / Hidden Single|Pointing / Claiming|Pair / Triple|
|---|---|---|---|
|singles|有効|無効|無効|
|locked|有効|有効|無効|

`LOCKED_CANDIDATES=0` を `deduction_engine` と `fades_core` に追加した。
既定値は1。専用ベンチマークターゲットから構成を指定する。
今回の比較対象 `locked` は #11 のモード4ではなく、Singles＋Locked Candidatesの基準構成。

### deduction: 推論単体

`deduction_engine` 自体は組み合わせ回路であり、クロック端子はない。
入力を「ヒントは1候補、空欄は9候補」の729 bit状態に変換し、
**1回の組み合わせ評価と状態更新を1サイクル**として反復する。
完成・矛盾・固定点のいずれかを認識した評価も1サイクルに数える。
したがって、更新回数だけを数える定義より終端判定の1回が多い。
解けなかった問題を除外せず、停滞した問題も平均に含める。

### core: 探索込みの実行区間

実際の `fades_core` RTLを用い、各問を空のキューに入力してRUN開始から
`event_finish` までを測る。推論、分岐、矛盾処理、分岐の復帰・ロードを含む。
**初期投入・最初のロード、結果の排出、次問の供給待ちは計測外**。
問題間のロードやRAM先読みを含む連続処理の実測スループットではない。
このため既存のキュー先行投入式 `core_test` の平均とは定義が異なる。
Kaggleには分岐がなく、推論単体と同じサイクル数になった。

全ての完成出力についてヒント保持・行列ブロックの正当性を確認。
KaggleではCSVの正解列との一致も全件確認し、推論単体で残った候補にも
正解が保持されていることを検査した。17ヒント・難問の今回の専用ベンチマークでは
独立CPU参照解との照合は行わず、完成盤面の数独制約と入力制約を確認している。

## 3. Kaggleの理論性能

演算上限は、十分な問題が常に供給され、出力待ちがなく、各エンジンに1サイクルの
推論経路を実装できるという条件で以下となる。

```text
R_compute = N × f_core / 4.899026
R_actual <= min(R_compute, R_input, R_output, R_dispatch, R_collect, R_PS/DDR)
```

1問ごとに独立のロードサイクルを挟む実装なら分母を5.899026とする。
完成と次問ロードを重ねれば、この1サイクルを隠せる可能性がある。
以下の100/150/200 MHzは設計検討用の仮定であり、Singles回路の到達周波数は未測定。
搭載可能コア数も合成・配置配線で確認した値ではない。

|コア数|100 MHz 演算上限 M問/s|150 MHz|200 MHz|100 MHzで1問1ロード追加 M問/s|100 MHz演算上限に必要な入力GB/s|同・入力＋出力GB/s|
|---|---:|---:|---:|---:|---:|---:|
|6|122.473|183.710|244.947|101.712|7.838|15.677|
|8|163.298|244.947|326.596|135.616|10.451|20.902|
|16|326.596|489.893|653.191|271.231|20.902|41.804|
|32|653.191|979.787|1,306.382|542.462|41.804|83.608|

GB/sは10^9 byte/s、64 byte入力＋64 byte出力を仮定。
DMAの読書き以外のPSコピー・キャッシュ処理・descriptor等は加算していない。
例えば16コア100 MHzの演算能力をそのまま使うには、**各方向20.90 GB/s**が必要になる。
コアだけを軽量化しても、これを既存のDDR接続で達成できるとは言えない。

## 4. issue #11 と供給能力

参照: [#11 Kaggle最終まとめ](https://github.com/void-hoge/fades/issues/11#issuecomment-6659577990)。
issueの測定は別のKaggle **900万問CSV**を使っている。
今回の100万問集合とはデータも測定範囲も異なるため、以下は供給系の参考値。

- 全900万問をrotating windowsで供給: 約 **3.14 M問/s**。
  約10秒のうち入力準備・コピーが約9.25秒、kernel RUN合計は約0.74秒。
- 準備済みDDRの先頭131,072問を反復: 約 **43 M問/s**。
  core 100→115.385 MHzでも差がほぼなく、転送系律速が示唆された。
- 同issueの測定はCPU参照・出力内容検査なし。今回のRTLベンチマークは上記の検査あり。

### 現行経路の上限

`rtl/fades.sv` は入力・出力とも1問64 byte、ストリーム128 bit、4 beat/問。
DMA実187.5 MHzなら理想的に連続転送できても **46.875 M問/s/方向**。
DDR payloadは入力3.0 GB/s＋出力3.0 GB/s。
実測約43 M問/sはこの92%程度に相当するが、これだけで個別の律速箇所を断定はできない。

Singles・100 MHzでは **3エンジン**で演算上限61.24 M問/s、
1ロード追加を数えても50.86 M問/s。平均的には既存DMAの理論上限を超える。
コアの所要時間変動を吸収するキューは必要だが、同じ転送経路に8〜32コアを
接続するだけでは、その演算能力は使い切れない。

さらに現行の中央dispatchとcollectは各core cycleに最大1問。
core 100 MHzなら、DMAを高速化してもそれぞれ **100 M問/s**が別の上限になる。
入出力は独立なので、両者を加算して50 M問/sとするものではない。

## 5. 推奨アーキテクチャ

### A. まずPSの再充填を解消する

`host/tools/fades_benchmark.cpp` の `Batch::prepare` は、問ごとにレコードを作り、
IDを書き直してDMAバッファへ64 byteコピーしている。現状は供給準備とRUNが直列。

1. 入力をあらかじめDMA用のバイナリ形式へ変換し、問ごとの再パックをなくす。
   IDも保存時に固定するか、PLで連番を付けてPSの書き換えをなくす。
2. 大きな連続バッファを一度だけ準備してSGで消費する。
   100万問なら64 MB、900万問なら576 MBの入力レコードになる。
   実際には連続物理メモリの確保方法、DMAマップ、バッファ寿命の設計が必要。
3. 全件常駐が難しければ、producer/consumer方式のリングで準備と転送を重ねる。
   driverのRUN単位で全スロットの完了を待つ構造も、連続submit/reap型へ見直す。

約3.14→43 M問/sの差が大きいため、まずここを測定・改善する価値が高い。
ただしコピー速度が消費速度より低ければ、二重バッファだけでは平均供給能力は増えない。

### B. 多数の推論エンジンと少数の探索コアを分ける

```text
packed input → 小さな共有/バンク別キュー → Singlesエンジン群
                                         ├ 完成 → バンク別結果キュー
                                         └ 停滞 → 探索キュー → 探索コア → 結果
```

- Singlesエンジンは現在の729 bit状態と変更・矛盾metadataを保持するだけにし、
  各エンジンに1024段の探索・問題RAMを複製しない。
- 停滞した問題はIDと候補状態を探索側へ渡す。候補状態729 bitは元の324 bit盤面より広く、
  フォールバックキューの幅も計上する必要がある。
- 今回の100万問では探索側への流量は0。ただしこの集合だけから任意の入力も探索不要とは言えない。
- 17ヒントでは55.44%、Hardでは100%が探索側へ流れる。
  この用途では探索側の処理能力も含めて均衡させる必要があり、Singlesエンジン数だけ増やせない。

BRAMの根拠は既存main6コアの `results/clock_main_115_actual_checked/utilization.rpt`:
128/144タイル、LUT 89,622/117,120。
各コアのRAMは729×1024=746,496 bitで、理想的なbit容量だけでも20.25 BRAM36相当。
6コア分で121.5相当を占める。実配置では幅・ポート・周辺FIFO等の丸めもある。
規則削減による実LUT削減量は本実験では未評価。

全エンジンに探索を残す場合でも、共有入力キューと探索stackを分離し、
stack専用RAMを縮小する設計が候補になる。現行は最悪324個の兄弟状態を予約する。
512段にして入力キューを共有化すれば容量は減るが、単なる定数変更では済まず、
占有数・最悪探索深さ・BRAMポート競合の再検証が必要。

### C. DMA以降はバンク化して段階的に広帯域化する

- 512-bit × 187.5 MHz、1 beat/64 byteにすれば、ストリームの理論上限は
  **187.5 M問/s/方向**。ただしDDR/AXIメモリ側の実帯域も増やす必要がある。
- 100 MHzで中央1問/cycleのままでは100 M問/sが残る。
  dispatch・collectをバンクごとに設け、エンジンへの729 bit全体の大きなmuxも局所化する。
- 8エンジン100 MHzの163.3 M問/sには最低2問/core cycleの並列供給・回収、
  16エンジンの326.6 M問/sには最低4問/core cycleが必要。
  後者は512-bitストリーム1本の187.5 M問/sも超える。
- 入力だけ広げると出力が律速する。全解を返すなら両方向を同時に設計する。
  集計だけでよい用途ならPL内で件数・checksum等へ縮約する別のABIも考えられるが、
  全解回収とは提供する結果が異なる。

64 byte中にはpaddingもあるが、現形式の意味のあるデータだけでも
入力はID64＋セル324=388 bit、出力はID64＋status8＋セル324=396 bit。
レコード境界をまたいで最密充填しても現形式のpadding除去は約1.3倍にとどまり、
コア数を何倍にもするための帯域増加を単独では賄えない。

### 次の実験の順序

1. PSのバイナリ入力・連続リング化を測り、現行回路で全件供給時も約43 M問/sに近づくか確認。
2. Singles専用エンジンの資源・到達クロックを合成/配置配線で測り、
   `N × f / 4.899026` と実装可能な入出力帯域から適正コア数を選ぶ。
3. バンク化した供給・回収と広幅DMAを統合シミュレーションで測り、
   問題待ち・結果待ち・fallback待ちを別カウンターで評価する。

## 6. 再現

入力 `sim/data/kaggle1million.csv` はローカル配置ファイル（Git管理外）。
SHA256: `5a77d5392c19c783db68961e000c17fda246f1e362655dc9675f3e7cd4f57bd6`。
全1,000,000行を使い、先頭抽出・サンプリングは行っていない。

```sh
cmake --preset host
cmake --build --preset host --target deduction_bench_singles deduction_bench_locked \
  core_bench_singles core_bench_locked deduction-singles-build --parallel 4
python3 sim/deduction_engine/benchmark_cycles.py --jobs 4
ctest --preset host -L '^deduction_engine$' --output-on-failure
verilator --lint-only --language 1800-2017 -Wall --top-module fades_core \
  -GLOCKED_CANDIDATES=0 rtl/deduction_engine.sv rtl/branch_generator.sv rtl/fades_core.sv
```

各実行ファイルは `DATASET OUTPUT.csv [LIMIT]` を受け取る。
生成先は `build/host/sim/deduction_engine/`。CSVは `quizzes,solutions` または
`puzzle,solution` ヘッダー付き2列、あるいは1行81文字の既存形式に対応する。
無指定のLIMITは全件。欠損・不正形式・タイムアウトはエラー終了する。

検証: 12通りの全件測定成功、既存推論の有向試験・形式検証4件成功、
Singles専用の規則選択/Single伝播/矛盾の有向試験成功、
既定構成とSingles構成のcore lint成功。今回はRTLサイクル測定までで、
上記の多コア構成・新供給アーキテクチャの物理実装値・実機値はまだ含まない。
